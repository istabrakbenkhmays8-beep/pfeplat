1. Introduction & context

1.1 Background — Advancia Training

Advancia Training is the leading authorized training centre in Tunisia for major vendor certifications: Microsoft, Cisco, Fortinet, EC-Council, PECB, PMI, Palo Alto Networks, IBM, Pearson VUE, PSI, CompTIA, PeopleCert and Togaf. The company delivers live online, on-site (in their Tunis campus) and corporate intra training, plus official certification exams. The June 2026 calendar alone contains over 30 distinct certification tracks across 8 competency domains (Networking, Security, Cloud, Data & AI, Systems, DevOps, Business, Architecture).

1.2 Problem statement

Today, prospective trainees discover Advancia's catalog through static brochures and a content-only website. There is no integrated platform to:

  • browse the live catalog with filters by partner, domain, mode and price;
  • register, enrol, and consume content (live links, on-site reservations, self-paced PDF/video);
  • take a final assessment and receive a verifiable certificate;
  • let learners earn and spend an in-platform currency to reduce the cost of certifications;
  • give the administration a unified back-office with imports/exports, audit trail and trainer assignment;
  • give super-administrators an AI agent that can both advise and act on guarded services with human-in-the-loop confirmation;
  • expose the same backend to a companion mobile app.

1.3 Objectives

  • Functional: deliver a Udemy-style learner experience (content-dense cards, sticky enrol panel, clean learning view) rebranded to Advancia's red / white / black identity, with smooth motion, real imagery and dark + light themes.
  • Operational: give admins a back-office with KPI cards, charts, filterable tables, Excel/PDF exports, XLSX imports, calendar of sessions, and email-on-confirm for trainer assignment.
  • Governance: give the super-admin full control of admins, reservations, trainers, audit log, and a built-in AI agent that orchestrates guarded services with HITL confirmation on mutating actions.
  • Accessibility: tri-lingual (EN / FR / AR with RTL), fully responsive (mobile, tablet, desktop), plain non-technical wording — the audience is not IT experts.
  • Extensibility: a single REST API consumed by both the web app and an Expo / React Native companion.

1.4 Methodology & build order

The project was built in 12 verifiable phases, each compiling and tested before the next began:

  1. Scaffold (Next.js + TS + Tailwind v4 + theme + responsive shell);
  2. Models + DB (Mongoose schemas, indexes, validation);
  3. Auth (register + verify, login JWT, forgot/reset, RBAC middleware);
  4. Public site (home, catalog, course detail, contact);
  5. User space (3 learning modes, assessments, certificates, wallet, games, leaderboard);
  6. Payments (mock + Paymee / Konnect / Flouci adapter; partial pay coins + card);
  7. Admin space (CRUD + filters + XLSX import + Excel/PDF exports + dashboard);
  8. Calendar (month / week / day, shared user/admin views);
  9. Super-admin space (admin management, reservations, audit, trainer assignment + email);
  10. AI layer (User chatbot · Admin chatbot · Super-Admin agent with tools + HITL);
  11. i18n (EN / FR / AR + RTL across web and mobile);
  12. Mobile app (Expo scaffold consuming the same API);

Plus a final Polish & Deploy phase — animations pass, empty/loading/error states, copy review, then hosting on Vercel + MongoDB Atlas for a shareable URL.

4. System architecture

4.1 Layered MVC + Service + Repository

The architecture enforces a strict 5-layer separation. Controllers stay thin; business rules live in services; only the repository layer talks to Mongoose. The same API is consumed by the web app and the mobile app. The AI agent calls the same guarded services — it never bypasses business logic or RBAC.

4.2 Folder structure

app/                              # Next.js App Router — route groups per actor
  (public)/                         # visitor: home, catalog, course detail, contact, auth
  (user)/                           # learner space — protected by middleware
  (admin)/                          # admin space — protected
  (super-admin)/                    # super-admin space — protected
  api/                              # API routes → call controllers
src/
  controllers/                      # parse request → call service → format response
  services/                         # business logic (coins, payments, certificates, ai, exports…)
  repositories/                     # persistence layer — the ONLY layer that touches Mongoose
  models/                           # Mongoose schemas + indexes (15 collections)
  lib/                              # auth, rbac middleware, zod validators, mailer, ai, pdf, xlsx, env
  i18n/                             # en / fr / ar dictionaries + RTL handling
  data/                             # seed data: catalog of 20 categories + 30 courses + 30 sessions
components/                         # React UI (server + client), shared design system
  layout/   ui/   cards/   home/    # composed by concern
public/                             # images, brand assets, logos
mobile/                             # Expo React Native app — consumes the same API
scripts/                            # tsx scripts: seed, exports, one-shot migrations

4.3 Request lifecycle (example: super-admin assigns a trainer)

  1. Browser POST /api/super-admin/sessions/[id] with { trainerId }.
  2. Middleware reads the JWT cookie, decodes role → verifies role === "super_admin", else 403.
  3. Controller validates body with Zod, calls sessionService.assignTrainer(sessionId, trainerId, actor).
  4. Service orchestrates: sessionRepo.update(...), auditRepo.write(...), emailService.sendTrainerAssignment(...).
  5. Repository persists via Mongoose; auditLog records before/after; SMTP sends the trainer their schedule.
  6. Controller returns the updated session JSON to the browser.

Every step has a single responsibility and is unit-testable. Replacing the email provider (Brevo → Resend → Mailtrap) is one file change in emailService.

6. Feature walk-through (with screenshots)

6.1 Public landing page

The home page targets the visitor. It opens with a video hero announcing the next training planning, a search bar wired to the catalog, a "Learn the way you want" three-card section explaining the three learning modes (In-person, Remote, Corporate intra), a partner grid with brand-tinted vendor logos (Microsoft, Cisco, Fortinet, EC-Council, PECB, PMI, Palo Alto Networks, IBM, Pearson VUE, PSI, CompTIA, PeopleCert, Togaf, Linux), a domain grid with real imagery for each competency area, headline statistics, a testimonials carousel from alumni, and a marquee carousel of partner marks.

6.2 Catalog

The catalog is a filterable grid. The left rail offers two facets driven by aggregations on the courses collection: partner (Microsoft, Cisco, Fortinet…) and domain (Security, Cloud, Data & AI…). The grid shows 30 published courses with hero image, vendor + level + duration, code chip and a hover lift. Search is wired through a query param. The same page is reused for filtered views like /catalog?vendor=Microsoft, called from the home-page partner tiles.

6.3 Course detail

Each course slug renders a Udemy-style detail page: hero with title + vendor + duration, "what you'll learn", learning mode badges (online / on-site / self-paced), pricing in TND, coin reward on completion, next scheduled session, and a sticky enrol panel on the right rail. Mobile collapses the right rail to a bottom call-to-action.

6.4 Trainings calendar

Shared component used by both learners and the back-office. Month / week / day views over the sessions collection, filtered by category, mode, trainer and status. Clicking a session opens its detail. Learners see "what they can join"; admins/super-admins see and manage everything.

6.5 Contact page

Public page with company info, an embedded location, and a contact form (name, email, subject, message). The form runs through Zod validation, persists the message and emails Advancia's CONTACT_INBOX via the same EmailService adapter.

6.6 About page

Brand storytelling page with the company's mission, what makes Advancia different (real partners, real trainers, real campus in Tunis), the partners marquee and the network map.

6.7 Authentication

Email-and-password authentication via the NextAuth credentials provider with the JWT strategy (stateless). New accounts start as pending_verification; a hashed one-time token is emailed (no session enumeration). Forgot-password follows the same hashed-token pattern with a 30-minute expiry. The signed JWT carries the user's role for the RBAC middleware to read on every API call.

6.8 Learner dashboard

"My space" lands the learner on their dashboard: current enrollments with progress bars, next live session, recently issued certificates, coin balance and streak. Plain-language KPIs ("Active learners", "Courses this month") instead of jargon.

6.9 Wallet & coins economy

Coins are an in-platform currency. Anti-abuse rules enforced server-side: coins are awarded only on first completion and passing the assessment; the enrollment is then flagged coinsAwarded so re-completion never re-credits. A configurable rate converts coins to discount on paid courses (e.g. 100 coins = one free course or a % off). Every change writes a CoinTransaction (append-only ledger).

6.10 Leaderboard, streaks & badges

Gamification layer: a global leaderboard ranks learners by total coins earned this month; a streak counter rewards consecutive learning days; badges mark milestones (first certificate, 5 courses, 1000 coins).

6.11 Certificates

On passing a course assessment, a branded PDF certificate is generated server-side with @react-pdf/renderer. The certificate URL is stored on the Certificate document so it can be re-downloaded any time.

6.12 Admin dashboard

The admin dashboard opens with KPI cards (active learners, published courses, sessions this month, completion rate), then two charts (enrollments & completions over 8 weeks; courses by domain — donut), then a bar chart of "Courses by partner" and a "Recent sign-ups" table. The left sidebar gives access to Courses, Categories, Sessions, Users, Calendar, Imports, Exports.

6.13 Admin · Courses CRUD

Filterable table with bulk publish / unpublish, in-place edit, hero-image upload, category and partner assignment. Reuses the same filter component as the public catalog.

6.14 Admin · Users table with Excel / PDF exports

Single large table with the columns from the spec: First name · Surname · Email · Gender · Age · Country · Level · Courses/Trainings joined · Coins · Status · Registered on. Filters (role, status, country, level, date) reduce the rows; the same filtered set is exported.

  • Excel export: xlsx (SheetJS) with a styled header row, auto column widths, freeze panes.
  • PDF export: html2pdf.js in landscape with repeating header row, page numbers and the Advancia logo as a header — a single rendering path so what the admin sees is what they get.

6.15 Admin · Sessions

List of all scheduled sessions across courses with quick filters and a one-click "create session" wizard pre-filling the course context.

6.16 Super-admin dashboard

The super-admin lands on a wider view: admin activity feed, pending reservations badge, sessions missing a trainer, audit log preview. From here they can also start a conversation with the AI agent.

6.17 Super-admin · Manage admins

Only the super-admin can create, suspend or delete admins. The action is audited.

6.18 Super-admin · Reservations

Reservations sit in a queue with capacity validation. Approving one locks the schedule, increments the session attendee count, and (if a trainer is already assigned) sends the trainer their updated roster.

6.19 Super-admin · Trainers + auto-email on assignment

Trainer records are data-only. Assigning a trainer to a session triggers an email containing the date/time, location or meeting link, the course, and the enrolled count. The email content is composed by the emailService.sendTrainerAssignment template; the transport is one swappable adapter (SMTP / Brevo / Resend / Mailtrap for dev).

6.20 Super-admin · Audit log

Every mutating action (admin/super-admin/agent) writes an AuditLog row with the actor, action verb, target type+id, and JSON of before / after. The view is filterable by actor and date.

6.21 The AI layer (the differentiator)

All AI flows go through a single server-side AIService adapter — swappable provider, tool calling, streaming, rate-limited, keys never exposed to the client. Three role-scoped assistants:

6.21.1 Super-Admin Agent (acts + advises)

Tools map 1:1 to existing guarded services (RBAC checked server-side, the agent cannot bypass it): createCourse, updateCourse, assignTrainer (fires email), createSession, approveReservation, createAdmin, exportData(type, format), importData, getAnalytics(metric). Human-in-the-loop: mutating actions go propose → super-admin confirms → execute. Read-only tools run directly. Proactive mode reads KPIs and suggests next steps ("3 sessions next week have no trainer — assign now?").

6.21.2 Admin Chatbot (advisory)

Read-scoped to admin data. Answers "how do I…" in plain language and surfaces pending items (courses without a category, users awaiting verification, imports to review) with deep links. No destructive actions.

6.21.3 User Chatbot (advisory, RAG over own profile)

Personalized from the user's enrollments: recommends next course / learning path, shows coin balance and how to earn more, nudges incomplete courses, explains certificates, suggests games.

6.22 Payments (TND-friendly, Stripe-free)

Since Stripe is unavailable in Tunisia, payments target Paymee / Konnect / Flouci through one PaymentService adapter, with a mock provider for the demo. A purchase can combine card + coin wallet (partial payment). Every successful checkout writes a Payment and a corresponding CoinTransaction if coins were spent.

6.23 Imports (XLSX)

Admins can bulk-create users, courses or enrollments by uploading an XLSX file. Each row passes Zod validation server-side; the import report shows the count of inserted / updated / skipped rows and the validation errors per skipped row.

7. Security, authentication, RBAC

7.1 Authentication

  • Strategy: NextAuth.js v4 with the credentials provider and the JWT session strategy. Stateless — no session store needed.
  • Password storage: bcryptjs with a 12-round cost.
  • Email verification: on registration, the account is created with status="pending_verification"; a one-time token (random 32 bytes, hashed with SHA-256) is stored on emailtokens with a 24h expiry. Clicking /verify?token=… activates the account.
  • Password reset: identical token pattern with a 30-min expiry. The "forgot password" endpoint always replies "If this email exists, we've sent a link" regardless of the email's existence — no enumeration.
  • JWT contents: sub (user id), email, role. Signed with NEXTAUTH_SECRET (32-byte random).

7.2 RBAC middleware

Every /api/* route group has a thin guard at its layout level. The guard:

  1. reads the NextAuth session cookie;
  2. verifies the JWT;
  3. looks up the route's required role from a config map;
  4. returns 401 if no session, 403 if role mismatch, otherwise calls the controller with the decoded actor.

Routes are grouped under app/(user)/, app/(admin)/, app/(super-admin)/ so the URL space mirrors the permission model.

7.3 Input validation & sanitization

Every controller validates its input through a Zod schema colocated next to it. Zod parses → strips unknown fields → throws on shape mismatch. Mongoose then validates again at the model level. This double validation eliminates an entire class of "trusted-client" bugs.

7.4 Rate limiting & lockout

  • Auth endpoints: 5 attempts per IP per 10 minutes; after 10 failed logins the account is temporarily locked.
  • AI endpoints: 30 requests per user per minute to keep costs predictable.

7.5 File uploads

multer in memory mode with a strict mime-type whitelist (avatar: image/jpeg|png|webp; XLSX import: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet) and a 5 MB cap.

7.6 Audit log

Every admin / super-admin / agent action writes an immutable AuditLog row: actor, verb, target, before / after JSON, timestamp. The super-admin's "Audit" view filters by actor and date.

7.7 AI safety

  • API keys never leave the server — the client calls /api/ai/chat, never the provider directly.
  • Tool calls are limited to the role's allowlist; the agent cannot invent a tool name that doesn't exist in the registry.
  • Mutating tools require HITL confirmation from the super-admin before execution.
  • Each agent tool call is auditable just like a human action.

8. Internationalization (EN / FR / AR + RTL)

8.1 Dictionary structure

Three dictionaries (en.ts, fr.ts, ar.ts) live under src/i18n/dictionaries/. Each exports a single typed object whose shape is defined in en.ts as the source of truth — TypeScript will fail to compile if a translation key is missing in any locale.

// src/i18n/dictionaries/en.ts (excerpt)
export const en: Dict = {
  home: {
    browseByPartner: "Browse by partner",
    browseByPartnerBlurb: "Authorized training and exams across the vendors we cover.",
    seeAllCourses: "See all courses",
    // …
  },
  // …
};

8.2 Resolution

The locale is read from a cookie on first render (falls back to en). A getT() helper in src/i18n/server.ts returns the resolved dictionary and the active locale, used inside Server Components without any client-side hydration cost.

8.3 RTL handling

For Arabic (ar), the root <html> element gets dir="rtl". The layout uses Tailwind's logical properties — ms-* / me-* instead of ml-* / mr-*, ps-* / pe-* instead of pl-* / pr-*. The grid, flex, and typography therefore mirror automatically without per-direction overrides.

8.4 Switcher

The header has a language switcher (EN / FR / AR). It writes the chosen locale to a cookie and refreshes — the next render uses the new dictionary and (for AR) flips direction.

8.5 Mobile app i18n

The Expo app reuses the same three dictionaries (it imports from the shared src/i18n via the monorepo). Direction is set on the root navigation container.

10. Limitations, future work, conclusion

10.1 Known limitations of the demo

  • Mock payment gateway until Advancia provides Paymee or Konnect credentials.
  • SMTP in dev only (Mailtrap-captured) — production wiring requires Advancia's transactional sending domain.
  • AI keys optional — without an Anthropic key the chatbot UI shows a "not configured" hint and the agent tools panel is read-only.
  • Mobile parity — admin/super-admin remain web-first; mobile is scoped to visitor + learner for the first release.

10.2 Future work (post-PFE roadmap)

  • Live classroom integration — generate Teams / Meet links automatically when a session is created online.
  • Calendar (.ics) feed per learner so sessions land in Google Calendar / Outlook.
  • Notification center in-app (currently email-only).
  • Coupon codes + corporate billing for enterprise contracts.
  • Atlas search for typo-tolerant catalog search; today the search is a literal regex.
  • Pen-test pass — full OWASP Top-10 review before opening registration to the public.

10.3 What this PFE delivered

  • A production-grade, multi-role training platform end-to-end — public site, learner space, admin and super-admin back-offices, AI layer, audit log, calendar, gamification.
  • 20 categories · 30 courses · 30 June-2026 sessions seeded, with three fixture users covering all roles.
  • A live URL on Vercel + an Atlas-backed production database.
  • A companion Expo mobile scaffold consuming the same API.
  • Tri-lingual UI (EN / FR / AR) with full RTL.
  • A swappable AI service supporting Anthropic Claude and Groq via the same interface.

10.4 Personal takeaway

Building Advancia Training Platform was an exercise in discipline more than complexity — the trick was not to add features, but to keep the same architectural rules ("controllers never touch Mongoose", "agent calls the same services humans call, with the same RBAC") across 15 schemas, three role spaces, two languages of i18n + RTL, and a deploy target. Every shortcut was tempting, and almost every shortcut would have come back as a bug. The 12-phase build order (each phase verifiable) made it possible to keep the codebase compiling at every step instead of drowning in a six-month integration.
